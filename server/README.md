# podkop-server

VPS-панель для централизованного управления роутерами podkop: выдача ключей,
рассылка профилей маршрутов и публичный сайт, за которым панель живёт.
Компаньон к [3x-UI](https://github.com/MHSanaei/3x-ui) — сами ключи (VLESS)
создаются в 3x-UI через его API, а podkop-server хранит профили маршрутов и
отдаёт каждому роутеру его подписку.

## Как это работает

Один бинарь отдаёт две вещи:

```
        ┌──────────────────── VPS ─────────────────────┐
 гости ─┤  /            → девлог игры (публичный)       │
 оператор│  /<секрет>/  → NEWS (посты) + EXTRAS (панель) │
 роутеры │  /api/v1/…   → профиль маршрутов по токену   │
        └──────────────────────────────────────────────┘
```

- **Публичный сайт.** На `/` — девлог игры (по умолчанию Backfire; имя и слоган
  задаются в `.env` и должны совпадать с доменом): главная с лентой записей,
  страницы постов, roadmap и стек. Это не бутафория: сайт настоящий, посты
  пишутся через админку и живут в хранилище. Он же — легенда, за которой не
  видно панели.
- **Операторская область.** По секретному пути (`PODKOP_SERVER_ADMIN_PATH`,
  ссылок с сайта на него нет) — вход по логину/паролю и две группы экранов:
  **NEWS** (редактор постов) и **EXTRAS** — собственно панель podkop:
  OVERVIEW, CLIENTS, OUTBOUNDS, ROUTING, LOGS, CONFIG.
- **Раздача профилей.** Роутер периодически запрашивает
  `GET /api/v1/profile?token=<ключ>` и получает JSON-профиль, который применяет
  локально (см. `podkop/files/usr/lib/remote_config.sh` в корне репозитория).
  Каждый такой запрос отмечается как «последний контакт» — из него панель и
  строит статус клиента.

Что панель **не** знает: трафик, квоты и счётчики соединений. Это данные Xray,
их отдаёт 3x-UI, и подтягивать их podkop-server пока не умеет — вместо них на
экранах показывается то, что панель измеряет сама: когда роутер последний раз
приходил за профилем, сколько раз приходил, отстал ли от текущей ревизии
профиля, а также состояние хоста и собственный лог.

## Экраны

| Экран | Что показывает |
|-------|----------------|
| NEWS | Записи девлога: черновики и опубликованные, редактор с Markdown-подмножеством |
| OVERVIEW | Клиенты и профили, обращения за профилем по часам, CPU/память/диск, последние события |
| CLIENTS | Роутеры: профиль, последний контакт, число обращений, статус, поиск и фильтры, выдача и правка ключей |
| OUTBOUNDS | Точки выхода, выведенные из выданных ключей; TCP-проба по кнопке |
| ROUTING | Профиль как список правил, community-списки, «дрейф» — кто ещё не забрал новую ревизию |
| LOGS | Лог самой панели (в памяти с момента старта), фильтры по уровню |
| CONFIG | Переменные окружения (секреты замаскированы), сведения о сборке, безопасные действия |

Панель намеренно **не умеет** останавливать сервис и переписывать свой конфиг:
она работает в контейнере, конфигурация задаётся через `.env`, а кнопка «убить
себя» из веба — готовый способ потерять доступ. Из действий доступны только
перечитать хранилище с диска, проверить связь с 3x-UI и сбросить все сессии.

## Эндпоинты

| Путь | Назначение |
|------|-----------|
| `GET /` | Публичный сайт (или заглушка/форма входа — см. `PODKOP_SERVER_ROOT`) |
| `GET /post/{slug}` | Страница записи девлога |
| `GET /media/…` | Картинки постов, встроенные в бинарь |
| `GET /robots.txt` | Индексация сайта плюс Content Signals (см. ниже). Путь админки здесь **не** упоминается — файл публичный, и запрещающая строка выдала бы секретный путь всем подряд; операторская область закрыта заголовком `X-Robots-Tag` на своих же ответах |
| `PODKOP_SERVER_ADMIN_PATH` | Вход оператора, CMS и панель |
| `GET /api/v1/profile` | Профиль для роутера. Авторизация по `token` (query, `Authorization: Bearer` или `X-Podkop-Token`) |
| `GET /api/v1/sub` | Тот же ключ подпиской для клиентов на телефоне (base64-список ссылок). Авторизация та же. `/profile` им не подходит: это документ podkop, а не подписка |

Формат профиля (совпадает с тем, что ожидает клиент podkop):

```json
{
  "proxy_string": "vless://…",
  "community_lists": ["russia_inside"],
  "p2p_direct": true,
  "direct_ru_zones": true,
  "dns": { "type": "doh", "server": "https://dns.google/dns-query" },
  "update_interval": "1d"
}
```

## Конфигурация (переменные окружения)

| Переменная | По умолчанию | Описание |
|-----------|--------------|----------|
| `PODKOP_SERVER_ROOT` | `site` | Что на `/`: `site` (девлог), `decoy` (заглушка 4PDA), `login` (форма входа) |
| `PODKOP_SERVER_SITE_NAME` | `Backfire` | Название проекта в шапке, тайтлах и футере сайта |
| `PODKOP_SERVER_SITE_TAGLINE` | `an open-city street racer on s&box` | Подпись рядом с названием |
| `PODKOP_SERVER_SITE_INDEXING` | `false` | Разрешить поисковикам индексировать сайт; админка закрыта всегда |
| `PODKOP_SERVER_LISTEN` | `:8080` | Адрес прослушивания HTTP |
| `PODKOP_SERVER_STORE` | `/var/lib/podkop-server/store.json` | Файл хранилища (JSON) |
| `PODKOP_SERVER_ADMIN_PATH` | `/manage/` | **Секретный** путь операторской области (обязательно смените) |
| `PODKOP_SERVER_ADMIN_USER` | `admin` | Логин оператора |
| `PODKOP_SERVER_ADMIN_HOST` | — | Отдельный хостнейм для панели: его корень ведёт в операторскую область, а не на сайт. Только для хостнейма за Cloudflare Access |
| `PODKOP_SERVER_ADMIN_PASSWORD` | — | Пароль оператора (**обязателен**) |
| `PODKOP_SERVER_SESSION_TTL` | `12h` | Время жизни сессии, продлевается активностью |
| `PODKOP_SERVER_LOGIN_MAX_FAILS` | `5` | Неудачных входов подряд до блокировки |
| `PODKOP_SERVER_LOGIN_LOCKOUT` | `15m` | Длительность блокировки адреса |
| `PODKOP_SERVER_TRUSTED_PROXY` | `false` | Доверять `X-Forwarded-For` / `CF-Connecting-IP` |
| `PODKOP_SERVER_DECOY_DIR` | — | Своя заглушка вместо встроенной (при `ROOT=decoy`) |
| `XUI_BASE_URL` | — | URL 3x-UI (в compose — `http://3x-ui:2053`) |
| `XUI_USERNAME` / `XUI_PASSWORD` | — | Учётные данные 3x-UI. Пусто → ключи только вручную |
| `XUI_INBOUND_ID` | — | ID inbound в 3x-UI для новых клиентов |
| `XUI_PUBLIC_HOST` | host из `XUI_BASE_URL` | Хост/IP для генерируемых vless-ссылок |
| `XUI_CLIENT_FLOW` | — | XTLS flow новых клиентов (`xtls-rprx-vision`). Применяется только на TCP-инбаундах |

### Выдача ключей через 3x-UI

Панель читает inbound, создаёт клиента и собирает `vless://`-ссылку из
`type/security/sni/pbk/fp/sid/spx`, для gRPC добавляет `serviceName`, `mode` и
`authority`, для TCP — `flow` из `XUI_CLIENT_FLOW`.

Vision живёт только на TCP: если inbound gRPC или WebSocket, ключ выдаётся без
`flow`, а на экране LOGS появляется предупреждение. Это не ошибка — ссылка
рабочая, просто без ускорения. Для нестандартных транспортов всегда остаётся
ручной режим: скопировать ссылку из 3x-UI и вставить в поле PROXY LINK.

## Развёртывание

```sh
cd server/deploy
cp .env.example .env
# отредактируйте .env: секретный ADMIN_PATH, длинный пароль, способ доступа
docker compose up -d --build
```

Порт контейнера публикуется **только** на `PODKOP_SERVER_BIND` (по умолчанию
`127.0.0.1`), никогда на `0.0.0.0`. Дальше выберите одну схему доступа.

### A. Отдельный порт с TLS — `docker compose --profile public up -d`

nginx терминирует TLS на 8443 и проксирует в панель. Порт 443 занимать нельзя:
там Xray Reality, он отвечает на любой SNI и уводит незнакомый в маскировку.

- в `.env`: `PODKOP_SERVER_BIND=127.0.0.1`, `PODKOP_SERVER_TRUSTED_PROXY=true`;
- сертификат положить в `deploy/certs/` и указать домен в `nginx.conf`;
- панель становится видна сканерам портов — за это отвечают лимит попыток входа
  и секретный путь.

### B. Cloudflare Tunnel — `docker compose --profile tunnel up -d`

Портов на VPS не открывается вообще: `cloudflared` соединяется наружу сам, TLS и
домен — на стороне Cloudflare.

- в `.env`: `CLOUDFLARE_TUNNEL_TOKEN=…`, `PODKOP_SERVER_TRUSTED_PROXY=true`
  (иначе все запросы придут с адреса туннеля и одна неудачная попытка входа
  заблокирует всех);
- в туннеле → Public Hostname указывайте сервис **`podkop-server:8080`**:
  `localhost` не сработает, cloudflared живёт в соседнем контейнере;
- A-запись на IP сервера в DNS заводить не нужно — туннель пропишет CNAME сам.
  Оставшаяся ручная запись перебивает туннель и даёт ошибку 521;
- сертификат тоже не нужен: TLS терминирует Cloudflare своим Universal SSL,
  внутрь туннеля идёт обычный HTTP.

#### Веб-интерфейс 3x-UI за тем же Access

Своя панель 3x-UI намеренно не публикуется: контейнер отдаёт 2053 только на
`XUI_UI_BIND` (по умолчанию `127.0.0.1`), то есть с самого VPS —
`ssh -L 2053:127.0.0.1:2053 vps`, дальше `http://127.0.0.1:2053`. Если нужен
доступ снаружи:

1. **Сначала** уберите заводской логин: образ приезжает с `admin`/`admin` на
   пути `/`, и `./xui-creds.sh --reset` меняет и то, и другое. Публиковать
   форму входа с дефолтным паролем нельзя даже под Access — политика остаётся
   единственным, что стоит между ней и интернетом.
2. Заведите Access-приложение на будущий хост (`xui.example.com`) с той же
   политикой, что и у панели, — до того, как появится маршрут. Маршрут без
   политики открывает форму входа всем, а за ней все ключи сервера.
3. В туннеле добавьте hostname route: `xui.example.com` → `http://3x-ui:2053`
   (если 3x-UI поставлен скриптом на сам VPS, а не из этого compose —
   `http://host.docker.internal:2053`, для этого у `cloudflared` прописан
   `extra_hosts`).
4. Поднимите оба профиля: `./setup.sh` (или
   `docker compose --profile tunnel --profile xui up -d`).
5. Итоговый адрес — `https://xui.example.com/<webBasePath>/`; текущий путь
   показывает `./xui-creds.sh`.

`XUI_UI_BIND` при этом менять не нужно: cloudflared ходит в контейнер по
внутренней сети compose, а не через опубликованный порт, так что 2053 остаётся
на loopback и снаружи по-прежнему не отвечает.

Access здесь — единственный слой перед чужими глазами, поэтому политика должна
быть на конкретную почту/группу, а не «любой авторизованный».

### C. Совсем без публикации

Оба профиля выключены: панель доступна только с самого VPS или через ваш
туннель (см. настройку **Доступ к панели** на роутере). Тогда имеет смысл
`PODKOP_SERVER_ROOT=decoy` — публичного сайта в такой схеме всё равно никто не
увидит.

Собирается один статический бинарь без cgo — легко кросс-компилируется под
aarch64/arm64 VPS:

```sh
CGO_ENABLED=0 GOARCH=arm64 go build \
  -ldflags "-X main.version=$(git describe --tags --always)" ./cmd/podkop-server
```

## Первый ключ (телефон, без роутера)

Порядок, если нужен просто рабочий VLESS на устройство:

```sh
cd ~/podkop && git pull && server/deploy/setup.sh --admin-host panel.example.com
```

`setup.sh` правит `.env` сам (идемпотентно: повторный запуск пишет
«unchanged», а не вторую строку), поднимает профили `tunnel` и `xui`,
пересобирает панель и печатает учётные данные 3x-UI первого запуска вместе со
списком портов, открытых наружу. Полезные ключи: `--xray-port` (если 443
занят), `--profiles`, `--no-build`, `--no-trusted-proxy`. Прежний `.env`
сохраняется рядом как `.env.bak`. Если `.env` ещё нет, он заводится из
примера, а секретный путь и пароль генерируются и показываются один раз.

Правки, которые скрипт вносит, при желании делаются и руками — это
`PODKOP_SERVER_ADMIN_HOST`, `PODKOP_SERVER_TRUSTED_PROXY=true`, `XRAY_PORT` и
`XUI_UI_BIND` — после чего
`docker compose --profile tunnel --profile xui up -d --build`.

3x-UI при первом старте генерирует случайные учётные данные и случайный
`webBasePath` и пишет их в лог ровно один раз. Если строка уже уехала —
спросить у самого контейнера:

```sh
server/deploy/xui-creds.sh            # показать логин, порт и webBasePath
server/deploy/xui-creds.sh --reset    # задать новый пароль, если старый утерян
```

Интерфейс наружу не смотрит, заходить через туннель с локальной машины:

```sh
ssh -L 2053:127.0.0.1:2053 root@ВАШ_VPS
# затем в браузере http://127.0.0.1:2053/<webBasePath>/
```

Inbound: **VLESS**, Security **Reality**, Transport **TCP**, Flow
`xtls-rprx-vision`, порт — тот же `XRAY_PORT`. Reality-ключи генерируются
кнопкой в форме, dest/SNI берите с чужого сайта, который реально отвечает по
TLS 1.3 и не заблокирован в вашей стране. Дальше добавьте клиента, откройте у
него QR — телефон читает его любым современным клиентом (v2rayNG, Streisand,
Happ).

Адрес в ссылке — **голый IP сервера**. Домен, который смотрит в туннель, сюда
не годится: там CNAME на Cloudflare, и клиент придёт не на ваш Xray. A-запись с
серым облаком технически сработала бы, но заводить её не нужно и вредно, если
на том же домене живёт сайт: она публично связывает домен с IP, а туннель
ровно эту связь и прячет. Reality вашего домена не требует — в SNI идёт чужой
сайт, а адрес нужен только клиенту, у которого уже есть ключ.

### Почему в SNI не свой домен

Reality ничего не подписывает сам: чужое соединение он прозрачно переправляет
на dest, и проба получает настоящее рукопожатие с настоящим сертификатом того
сайта. Правдоподобие даёт dest, а не имя в SNI — подставив туда свой домен,
улучшить нечего.

Зато SNI идёт открытым текстом в каждом соединении. Это публичная связка «на
этом IP обслуживают такой-то домен», видимая провайдеру каждого клиента; домен,
за которым спрятаны сайт и панель, окажется в логах рядом с VPN-эндпоинтом, а
блокировка по SNI унесёт заодно и сайт.

Связный вариант со своим доменом всё же существует: положить сайт прямо на VPS
с собственным сертификатом, dest направить на локальный веб-сервер, A-запись
завести на IP с серым облаком. Тогда сходится всё — DNS, SNI и сертификат, и
несоответствия не видно даже при проверке. Цена: сайт лишается туннеля, IP
перестаёт быть скрытым, блокировка адреса уносит обе службы разом, а панель
теряет Access и остаётся только на секретном пути с паролем. Схема с
разделением выбрана ровно ради обратного.

Из этого следует, что сайт и VPN спокойно живут на одном VPS: посетители
приходят на адреса Cloudflare и до вашего IP не доходят, а обладатели ключа
знают IP, но не знают, что на нём сайт. Держите наружу только то, что должно
там быть — `ss -lntp` должен показывать на внешнем интерфейсе порт Xray и SSH,
всё остальное на `127.0.0.1`.

Если пароль 3x-UI уже задан и сохранён, менять его второй раз не нужно —
связка ставится отдельно:

```sh
server/deploy/xui-creds.sh --wire     # спросит пароль, ввод не отображается
```

Ту же команду нужно повторить после смены `webBasePath` из веб-интерфейса
3x-UI: `XUI_BASE_URL` включает путь, и без обновления панель начнёт получать
404 на выдаче ключей. `--wire` перечитывает текущий путь у контейнера.

Связку панели с 3x-UI `./xui-creds.sh --reset` делает и сам: пишет в `.env`
`XUI_USERNAME`, `XUI_PASSWORD`, `XUI_BASE_URL` (с учётом `webBasePath` — API
живёт под тем же путём, и без него панель получала бы 404) и `XUI_PUBLIC_HOST`,
если он пуст, после чего пересоздаёт контейнер панели. Отключается ключом
`--no-wire`. Руками останется только `XUI_INBOUND_ID` — номер созданного
inbound, если он не первый. Результат виден на экране CONFIG, строка XUI.

## Настройка роутера

Порядок важен: **сначала руками поднимите туннель** (вставьте `.conf`
AmneziaWG или ключ VLESS в podkop и убедитесь, что он работает) — только потом
включайте управление с панели. Иначе профиль неоткуда взять.

В LuCI podkop → Settings включите **Управление с VPS-панели**, укажите URL
панели, выданный ключ/токен и **Доступ к панели**, нажмите **Применить профиль
сейчас**. Дальше профиль обновляется по расписанию автоматически (и кэшируется
на случай, когда панель недоступна).

## Наполнение сайта

- Записи пишутся в **NEWS**: заголовок, слаг (пустой — выводится из заголовка,
  кириллица транслитерируется), тег, обложка, аннотация и текст.
- Разметка — подмножество Markdown: `#` заголовки, `-`/`1.` списки, `**жирный**`,
  `*курсив*`, `` `код` ``, блоки ``` ``` ```, цитаты `>`, `---`, ссылки
  `[текст](url)` и картинки `![alt](/media/file.png)`. Всё экранируется, а
  `javascript:`/`data:` в ссылках отбрасываются.
- Картинки — файлы из `server/web/site/media/`, они встраиваются в бинарь.
  Загрузки файлов через веб нет: media едет вместе со сборкой.
- Секции hero, roadmap и stack живут в `server/web/site/site.html` и правятся в
  репозитории.
- При первом запуске (`ROOT=site`) заводятся две стартовые записи — замените их
  своими.

## Индексация и Content Signals

`/robots.txt` отдаётся одним файлом, в котором сразу и преамбула Content Signals
Policy (та же, что кладёт managed robots.txt у Cloudflare), и правила сайта:

- `PODKOP_SERVER_SITE_INDEXING=false` (по умолчанию) — `Disallow: /` и
  `Content-Signal: search=no, ai-input=no, ai-train=no, use=immediate`;
- `true` — `Allow: /` с `search=yes`, а обучающим ботам (GPTBot, ClaudeBot,
  Bytespider и прочим из списка) отдельной группой `Disallow: /`.

**Managed robots.txt в Cloudflare при этом нужно выключить** (Security →
Settings → Bot traffic). Он не заменяет файл, а *дописывается перед* нашим, и
его `Allow: /` попадает в ту же группу `User-agent: *`, что и наш `Disallow: /`
— краулер видит противоречие и по правилам разбора выбирает разрешение. Всё,
ради чего эта настройка включалась, теперь есть в файле сервера.

## Замечания по безопасности

- Форма входа смотрит в интернет. Пароль — длинный и случайный; лимит попыток и
  TTL сессий включены по умолчанию, вход и отказы видны на экранах LOGS/EVENTS.
- `PODKOP_SERVER_TRUSTED_PROXY` включайте **только** когда перед панелью
  действительно стоит nginx или cloudflared. Иначе подделанный заголовок
  позволит обойти лимит или заблокировать чужой адрес.
- Держите `ADMIN_PATH` в секрете: ссылок с сайта на него нет, и он остаётся
  вторым слоем поверх пароля.
- Хранилище (`store.json`) содержит выданные ключи/токены — ограничьте доступ.
- Заглушка 4PDA (`ROOT=decoy`) — камуфляж входа в **собственную** панель. Не
  размещайте на ней реальную форму сбора учётных данных и не выдавайте её за
  чужой домен.
- **Самоблокировка.** Профиль с панели может сломать тот самый туннель, через
  который роутер до неё ходит. Последний рабочий профиль кэшируется на роутере
  (`/etc/podkop/remote_profile.json`), но менять через панель конфиг самого
  туннеля не стоит: держите его локальным, а с панели рассылайте только
  маршрутные настройки.

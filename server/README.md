# podkop-server

VPS-панель для централизованного управления роутерами podkop: выдача ключей,
рассылка профилей маршрутов и камуфляж админ-панели от активного зондирования.
Компаньон к [3x-UI](https://github.com/MHSanaei/3x-ui) — сами ключи (VLESS)
создаются в 3x-UI через его API, а podkop-server хранит профили маршрутов и
отдаёт каждому роутеру его подписку.

## Как это работает

По умолчанию панель **не публикуется в интернет вообще**: снаружи её порт не
открыт, TLS-сертификат не нужен, активному зондированию нечего находить. Роутер
приходит за профилем **изнутри туннеля**, который у вас уже поднят:

```
                 ┌──────────────── VPS ─────────────────┐
 роутер podkop ══╪══ туннель ══► podkop-server ─► 3x-UI  │
   (клиент)      │              (профили, заглушка) (ключи)
                 └──────────────────────────────────────┘
```

- **Заглушка (камуфляж).** На `/` отдаётся страница-приманка — визуально близкая
  к странице входа 4PDA. Её форма «мёртвая»: она никогда не проверяет и не
  сохраняет учётные данные, а всегда возвращает правдоподобное «Неверный логин
  или пароль». Это камуфляж собственной админки от активного зондирования — не
  сбор чужих учёток. Реальный вход оператора находится по **секретному пути**
  (`PODKOP_SERVER_ADMIN_PATH`).
- **Админ-панель.** По секретному пути оператор входит по логину/паролю, выдаёт
  ключи (вручную вставляя ссылку или создавая клиента в 3x-UI) и редактирует
  профили маршрутов, назначая их роутерам.
- **Раздача профилей.** Роутер (podkop) периодически запрашивает
  `GET /api/v1/profile?token=<ключ>` и получает JSON-профиль, который применяет
  локально (см. `podkop/files/usr/lib/remote_config.sh` в корне репозитория).

## Эндпоинты

| Путь | Назначение |
|------|-----------|
| `GET /` и любой прочий путь | Заглушка 4PDA (камуфляж). POST — «мёртвая» форма. |
| `PODKOP_SERVER_ADMIN_PATH` | Вход оператора и панель управления. |
| `GET /api/v1/profile` | Профиль для роутера. Авторизация по `token` (query, `Authorization: Bearer`, или `X-Podkop-Token`). |

Формат профиля (совпадает с тем, что ожидает клиент podkop):

```json
{
  "proxy_string": "vless://…",
  "community_lists": ["russia_inside"],
  "p2p_direct": true,
  "direct_ru_zones": true,
  "dns": { "type": "doh", "server": "https://dns.google/dns-query" },
  "update_interval": "1d"
}
```

## Конфигурация (переменные окружения)

| Переменная | По умолчанию | Описание |
|-----------|--------------|----------|
| `PODKOP_SERVER_LISTEN` | `:8080` | Адрес прослушивания HTTP. |
| `PODKOP_SERVER_STORE` | `/var/lib/podkop-server/store.json` | Файл хранилища (JSON). |
| `PODKOP_SERVER_ADMIN_PATH` | `/manage/` | **Секретный** путь админки (обязательно смените). |
| `PODKOP_SERVER_ADMIN_USER` | `admin` | Логин оператора. |
| `PODKOP_SERVER_ADMIN_PASSWORD` | — | Пароль оператора (**обязателен**). |
| `PODKOP_SERVER_DECOY_DIR` | — | Каталог со своей заглушкой (переопределяет встроенную). |
| `XUI_BASE_URL` | — | URL 3x-UI (в compose — `http://3x-ui:2053`). |
| `XUI_USERNAME` / `XUI_PASSWORD` | — | Учётные данные 3x-UI. Пусто → ключи только вручную. |
| `XUI_INBOUND_ID` | — | ID inbound в 3x-UI для новых клиентов. |
| `XUI_PUBLIC_HOST` | host из `XUI_BASE_URL` | Хост/IP для генерируемых vless-ссылок. |

## Развёртывание

```sh
cd server/deploy
cp .env.example .env
# отредактируйте .env: секретный ADMIN_PATH, пароль, PODKOP_SERVER_BIND,
# (опц.) креды 3x-UI
docker compose up -d --build
```

`docker-compose.yml` публикует панель **только** на адресе
`PODKOP_SERVER_BIND` (по умолчанию `127.0.0.1`) — никогда на `0.0.0.0`. `nginx`
и `3x-UI` вынесены в compose-профиль `public` и по умолчанию не поднимаются:
публичный фронт этой схеме не нужен, заглушку отдаёт сам podkop-server. Если
фронт всё же понадобится — `docker compose --profile public up -d`.

### Схема 1 — через VLESS (панель на loopback)

Подходит, когда на VPS уже стоит Xray (в т.ч. из Amnezia VPN) и порт 443 занят
им: ничего не трогаем, панель не конфликтует с маскировкой Reality.

- `PODKOP_SERVER_BIND=127.0.0.1`, панель слушает `127.0.0.1:8080`.
- На роутере: **Доступ к панели → Через прокси**, URL панели —
  `http://127.0.0.1:8080`. Запрос уходит в туннель через сервисный inbound
  podkop, и подключается к панели уже Xray на самом VPS — то есть `127.0.0.1`
  здесь означает loopback сервера, а не роутера.
- Если Xray работает в контейнере, его `127.0.0.1` — не loopback хоста:
  укажите `PODKOP_SERVER_BIND=172.17.0.1` (шлюз docker-моста) и такой же адрес
  в URL панели, либо подключите оба контейнера к общей сети.

### Схема 2 — через AmneziaWG (панель во внутренней сети туннеля)

- `PODKOP_SERVER_BIND=10.8.1.1` (адрес хоста в сети AWG) — либо, если AWG живёт
  в контейнере, подключите `podkop-server` к его docker-сети: раскомментируйте
  сеть `awg` и запись `- awg` в `podkop-server.networks`, подставив имя из
  `docker network ls`.
- На роутере: **Доступ к панели → Через маршрут в туннель**, интерфейс `awg0`,
  URL панели — `http://10.8.1.1:8080` (обязательно IP, не домен: podkop
  прокладывает точечный маршрут `/32` и не резолвит имя).
- Маршрут нужен потому, что podkop импортирует AWG-пиров с
  `route_allowed_ips=0` — иначе `AllowedIPs = 0.0.0.0/0` увёл бы в туннель весь
  трафик. Маршрут поднимается на `podkop start` и снимается на `podkop stop`.

Собирается один статический бинарь без cgo — легко кросс-компилируется под
aarch64/arm64 VPS:

```sh
CGO_ENABLED=0 GOARCH=arm64 go build ./cmd/podkop-server
```

## Настройка роутера

Порядок важен: **сначала руками поднимите туннель** (вставьте `.conf`
AmneziaWG или ключ VLESS в podkop и убедитесь, что он работает) — только потом
включайте управление с панели. Иначе профиль неоткуда взять: он лежит за тем
самым туннелем.

В LuCI podkop → Settings включите **Управление с VPS-панели**, укажите URL
панели, выданный ключ/токен и **Доступ к панели** (см. схемы выше), нажмите
**Применить профиль сейчас**. Дальше профиль обновляется по расписанию
автоматически (и кэшируется на случай, когда панель недоступна).

## Замечания по безопасности

- Заглушка — это камуфляж входа в **собственную** панель. Не размещайте на ней
  реальную форму сбора учётных данных и не выдавайте её за чужой домен для обмана
  пользователей — используйте только как визуальную «обёртку» админки.
- Встроенная заглушка — CSS-реконструкция без проприетарных ассетов 4PDA. Для
  продакшена задайте свой `PODKOP_SERVER_DECOY_DIR`.
- Держите `ADMIN_PATH` в секрете. Если всё же публикуете панель наружу
  (профиль `public`) — обязательно поднимите TLS, см. `nginx.conf`. Во
  внутренней схеме TLS не нужен: трафик и так идёт внутри туннеля.
- Хранилище (`store.json`) содержит выданные ключи/токены — ограничьте доступ.
- **Самоблокировка.** Профиль с панели может сломать тот самый туннель, через
  который роутер до неё ходит, — тогда управление потеряно до ручного
  вмешательства. Последний рабочий профиль кэшируется на роутере
  (`/etc/podkop/remote_profile.json`) и применяется при старте, но менять через
  панель конфиг самого туннеля не стоит: держите его локальным, а с панели
  рассылайте только маршрутные настройки (списки, зоны, DNS).
